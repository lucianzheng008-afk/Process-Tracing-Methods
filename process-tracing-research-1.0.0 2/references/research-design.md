# Research design

## Question diagnostic

Complete this sentence before selecting cases:

> In case(s) ___ during ___, the study asks how/why ___ produced or failed to produce ___ through ___, relative to ___, in order to revise/assess/explain ___.

Define:

- **Outcome:** category, threshold, onset, magnitude, and time.
- **Cause:** the active attribute capable of triggering a process, not a broad label.
- **Case:** an instance of a bounded theoretical relationship or a singular historical event.
- **Scope:** spatial, temporal, actor-level, institutional, and informational boundaries.
- **Contribution:** mechanism discovery, mechanism test, condition revision, or case explanation.

If C or O remains unknown, use exploratory comparison or soaking-and-probing before expensive process tracing.

## Population map

Do not inherit dataset codings uncritically. Recode cases using the concepts and temporal bounds relevant to the proposed mechanism.

| Case type | C | O | Main use |
|---|---:|---:|---|
| Typical | + | + | Build/test a mechanism that could operate |
| Deviant consistency | + | − | Trace breakdown after typical-case success |
| Deviant coverage | − | + | Explore another cause; not a direct test of C's mechanism |
| Irrelevant | − | − | Usually low value for tracing this mechanism |

For every candidate case record access conditions. A substantively ideal case with an opaque record may support only a design proposal.

When cases exhibit different outcome types, do not call them all typical instances of one undifferentiated O. Define whether they are (a) branches after a shared upstream process, (b) distinct outcomes requiring separate mechanisms, or (c) stages along one path. Use a structured focused comparison to discover branch points, then classify each case relative to its own bounded C/O claim.

## Case selection by design

### Theory-testing

Choose a typical case with C, O, and plausible context present. Select before operationalizing case-specific fingerprints. If prior confidence is low, conduct a modest plausibility probe; if evidence suggests a process and sources are adequate, deepen the design.

### Theory-building

Choose a typical case where many plausibly enabling conditions are present, because the mechanism's context is not yet known. For narrative comparison, use two similar typical cases, then test the inferred common mechanism within each.

### Theory-revision

Pair a deviant C+/O− case with a previously established typical C+/O+ case. Trace the known mechanism until it stops, then compare context and causal inputs at the breakpoint.

### Explaining-outcome

Select the outcome for substantive importance. Define “minimal sufficiency”: which important facets must the explanation cover, and what would make a part redundant?

## Mechanism heterogeneity audit

Before generalizing, ask whether a common C/O coding hides:

1. an omitted enabling or inhibiting condition;
2. different attributes within an OR-type concept;
3. degree thresholds that trigger different processes;
4. different temporal orders of the same conditions;
5. different weakest-link configurations.

Use **snowballing outward**: begin with the closest plausible case, then vary one context dimension at a time when possible. Each new case tests the boundary; it does not simply “replicate” the narrative.

## Time design

Record:

- process start and end;
- pre-treatment baseline;
- triggering event;
- expected lag for each step;
- critical junctures and decision windows;
- outcome onset versus later consolidation;
- archival or reporting delay;
- rival sequence expectations.
- shorter and longer outcome-window sensitivity checks when procedures differ across cases.

Guard against:

- defining the process backward from a known outcome;
- treating event order as transmission;
- using post-outcome statements as contemporaneous motivation;
- ignoring slow or cumulative mechanisms because traces are subtle before a threshold;
- allowing the outcome to appear inside the mechanism as a cause of itself.

## Priors and feasibility

Write a qualitative prior (`very low`, `low`, `medium`, `high`, `very high`) and justify it from:

- existing theory;
- cross-case knowledge, used cautiously;
- independent case-specific information available before the focal evidence.

Also rate record feasibility:

- source genres expected;
- legal/ethical access;
- preservation and declassification;
- language and technical barriers;
- asymmetric access across cases;
- whether elite motives are observable at all.

High prior does not excuse weak tests. Seek disconfirming high-certainty evidence. Low prior does not make any confirming observation decisive.

If theory/case literature is unavailable and the task forbids retrieval, use `unassessed`; do not invent a neutral `medium` prior. Continue by stating what literature would permit assessment.

If the task audits an already completed study or a prompt that reveals all focal evidence, label the prior as a **retrospective reconstruction**. Explain which information is excluded from that reconstruction and test sensitivity across a reasonable prior range.

## Design memo output

The design memo must state:

1. variant and mechanism resolution;
2. C, O, context, and time bounds;
3. case population and selection logic;
4. focal and competing explanations;
5. prior and source feasibility;
6. mechanism heterogeneity risks;
7. conclusion ceiling before evidence collection;
8. next-case strategy if the mechanism is supported.

For unequal-access comparisons, set a separate within-case conclusion ceiling for each case. The least accessible case caps common cross-case claims, not the warranted conclusion inside a richer case. Cross-case comparison must use a common evidentiary layer, while case-specific appendices preserve additional evidence.
